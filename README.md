# backoffice-agent

From operation logs to a safe tool-using agent, in two parts:

- **Part A, discover** (`process_mining/`): recover units of work from raw desktop/browser
  interaction logs, measure which back-office processes take the time, and build a case-queue
  assistant for the best candidate.
- **Part B, automate** (`sql_agent/`): an LLM agent that answers questions by writing SQL through a
  single guarded tool (`run_sql`), with an embedding router and read-only safety defences.

How they fit, honestly: Part A answers *what to automate and in what form*; its own conclusion for
the notes was that fixed templates beat an LLM. Part B shows *how to give an LLM a tool safely* when a
task does need open-ended queries. Part B runs on a separate dataset (Indian air-quality data from
OpenAQ), not on Part A's logs. Connecting the two (an agent that queries the mined case table) is a
next step, not something built here.

## Part A: process mining

### Problem
Two datasets of recorded work sessions in three mock business portals (HR, Finance, Logistics):
low-level events (clicks with DOM selectors or Windows UI Automation data, keystrokes, navigations,
window focus, screen text). Dataset A (63 sessions) has ground truth: which process was being run
when. Dataset B (15 sessions, ~20k events) has none. Tasks: (1) segment B into units of work with a
process label, (2) find which processes cost the most effort and why, (3) build something that
automates part of the best candidate.

### Approach
- Audit the data first; build the scorer before any segmenter (strict tolerances: boundary F1 at
  +-1/2/5 s, segment F1 at IoU >= 0.5).
- A case state machine: row click -> note -> commit, with fallbacks for missing telemetry (UI
  Automation clicks when the browser extension is absent, navigations when the mouse hook dies).
- Case type from the prefix of the portal case number (from DOM row id, table row, toast, cell text,
  then screen), because one screen can host two processes.
- Boundary lags calibrated on A (medians), scaled to B by B's measured tempo (no B labels used).
- Step 2: per-process time share, document lookups, keystrokes, recorded outcomes.
- Step 3: one engine + per-process definitions (`prototype/definitions.json`). Drafts the note and,
  for invoice matching, the decision; a person always confirms; every action is audit-logged.

## Part B: SQL agent

### Problem
Answer plain-English questions about a database (here: one year of daily PM2.5/PM10 readings, 60
monitoring locations, 10,959 measurements) without letting the model damage or exhaust the database.

### Approach
- **Router**: embed the question with `all-MiniLM-L6-v2`, pick the nearest of 14 reference questions
  by cosine similarity, and inject its SQL hint into the prompt.
- **Agent**: Llama 3.3 70B via Groq (`temperature=0`), LangChain `create_agent`, one tool: `run_sql`.
  Errors come back as text starting with `ERROR:` so the model can fix its SQL and retry.
- **Safety layer** (`tools/sql_tool.py`), every defence and what it stops:

| Defence | Stops | Evidence |
|---|---|---|
| SQLite opened with `mode=ro` (read-only URI) | any write, even if every check below were bypassed | backstop check PASS, `test_sql_safety.log` |
| Single statement: reject any `;` inside the query | stacked queries (`SELECT 1; DROP TABLE ...`), comment-then-stack | 4 stacking cases blocked |
| Allowlist: must start with `SELECT` or `WITH` | `DROP`, `EXPLAIN`, `PRAGMA` statements, empty input | blocked |
| Denylist of write/DDL/admin keywords anywhere (`INSERT UPDATE DELETE DROP ALTER CREATE REPLACE TRUNCATE ATTACH DETACH PRAGMA VACUUM REINDEX GRANT REVOKE`), case-insensitive | a write hidden in a CTE (`WITH t AS (...) DELETE ...`), mixed case | blocked |
| Row cap: append `LIMIT 100` if the query has none | accidental huge result sets flooding the model context | `probe_safety_gaps.log` |
| 5 s timeout via SQLite progress handler | runaway queries (infinite recursive CTE aborted at 5.00 s) | `probe_safety_gaps.log` |
| Errors returned as text, not raised | crashes; lets the agent self-correct | code |
| One tool only | the model has no file, shell or network access | code |
| API: empty question -> 400; failures -> generic 500 without stack trace; CORS limited to localhost origins | leaking internals; cross-site calls from other origins | `api.py` |
| SQLite default: extension loading disabled | `load_extension()` | `probe_safety_gaps.log` ("not authorized") |

Known gaps found while probing (`results/sql_agent/probe_safety_gaps.log`):
- The row cap is skipped whenever the text contains `LIMIT` anywhere: a caller's own `LIMIT 100000`, or
  a `LIMIT` inside a subquery, returns all 10,959 rows. The `[truncated to 100 rows]` note is then
  wrongly appended.
- The keyword denylist also matches inside string literals (`WHERE name LIKE '%Replace%'` is rejected).
- Schema reads are allowed (`sqlite_master`, `pragma_table_info(...)`); harmless here, but worth
  knowing.
- No defence against prompt injection through data values; impact is limited by read-only access.

## How to run

Python 3.10+.

Part A (standard library only):
```bash
cd process_mining/scripts
PROCMINE_DATA=<folder containing dataset_a/ and dataset_b/> python 01_audit_data.py   # then 02 ... 05
cd ../prototype && python extract_cases.py && python replay.py   # server.py for the demo
```
Only the `events.jsonl`, `gt.jsonl` and `*.json` files of the datasets are needed (no screenshots).
The data is not included.

Part B:
```bash
cd sql_agent
pip install -r requirements.txt
python data/generate_synthetic_air.py   # or fetch real data: fetch_openaq.py (needs OPENAQ_API_KEY)
python eval/ground_truth.py
python eval/test_sql_safety.py
python eval/run_routing.py
python eval/probe_safety_gaps.py
GROQ_API_KEY=... python eval/run_eval.py          # put the key in sql_agent/.env, never commit it
uvicorn api:app                                   # then open index.html
```
Note: the eval answer key is built from whatever database is present; the results above used the
real OpenAQ database (not included).

## Limitations

- Part A data come from a mock environment: queues of exactly 12 cases per run, compressed timings.
- Exception branches of most processes are never observed, so only P6 gets an automated decision draft.
- Part B's 14 evaluation questions are the router's own reference questions, so the end-to-end eval is
  in-distribution; the paraphrase test (11/14) is the only held-out check, and it covers routing only.
- Safety relies on regexes plus the read-only connection; the read-only connection is the real
  guarantee.
